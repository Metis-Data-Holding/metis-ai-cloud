# 老板 Demo、Serving Benchmark 与汇报设计

> 日期：2026-08-24
>
> 状态：已确认设计，等待实施
>
> 范围：业务闭环验收、分层性能测试、DeepSeek 官方参考、瓶颈判断与老板汇报材料

## 1. 目标

本轮工作回答两个问题：

1. 当前 Demo 是否已经打通“注册登录 → Playground → API Key → 标准 API → Usage / Billing → 管理日志”的核心业务闭环。
2. 当未来有一定数量用户使用时，系统首先受限于模型 / GPU、推理引擎、跨区域网络、Gateway、数据库 / Redis、公网链路还是其他环节。

最终面向老板的核心结论应能够被压缩为：

- 平台当前已经完成了什么真实闭环；
- 当前配置下建议的稳定并发是多少；
- 用户在该并发下能获得怎样的首 Token 延迟和生成速度；
- 第一个明显瓶颈在哪里，下一步最值得投入什么。

## 2. 非目标

本轮不以以下事项为目标：

- 证明当前 Demo 已达到 Production HA；
- 探测 DeepSeek 官方平台的容量上限；
- 用少量 Prompt 得出通用模型质量排名；
- 把页面 mock 性能数据、Tailscale ping 或单次成功调用当作 Benchmark；
- 实施自动路由、扩缩容、GPU Scheduler 或大规模平台重构；
- 在仓库、聊天、报告或截图中保存任何 API Key、Provider Credential 或其他 Secret。

## 3. 总体方法

采用三条相互独立但最终汇合的测试线：

### 3.1 业务闭环验收

验证真实用户路径：

```text
注册 / 登录
    ↓
Playground 选择模型并获得 Streaming 回复
    ↓
创建限模型、限额度、短期 API Key
    ↓
通过 OpenAI-compatible API 调用
    ↓
核对 Usage、余额、Token 额度和管理员日志
    ↓
调用未授权模型，确认 HTTP 403 且不计费
```

该测试回答“产品是否已经可以被用户完整使用”，不追求高并发。

### 3.2 本地 Gemma 分层容量测试

通过四条路径逐层增加系统组件：

| 层级 | 调用路径 | 主要观察对象 |
|---|---|---|
| A | Singapore 测试端 → LM Studio | 模型、GPU、LM Studio 原始能力 |
| B | BytePlus ECS → Tailscale → LM Studio | 跨区域网络额外开销 |
| C | ECS 本机 → metis-ai-cloud → LM Studio | Gateway、鉴权、路由、计费、PostgreSQL / Redis |
| D | 外部测试端 → Cloudflare → metis-ai-cloud → LM Studio | 真实公网用户体验 |

这些路径是“包含式路径对照”，不是可直接相减的组件计时。A、B、C、D 同时改变了压测发起端、连接方式和被测组件，因此不能把 A 与 B 的差值直接称为网络耗时，也不能把 C 与 D 的差值直接称为 Cloudflare 耗时。

测试记录必须同时标明“压测机 × 被测路径”。只有压测发起端、Prompt、连接复用和目标 Provider 等条件相同的配对实验，才可用于估计新增路径的总额外开销。其中 ECS 发起的 B 与 C 最接近嵌套路径，可用于观察加入 Gateway 后的整体变化，但仍需结合资源监控和补充实验后才能归因到具体组件。其余路径主要用于发现哪条完整用户路径异常。

### 3.3 DeepSeek 官方商业参考

通过 metis-ai-cloud 接入 DeepSeek 官方 `deepseek-v4-flash`，显式使用 non-thinking 模式，与 Singapore Gemma 使用相同任务集进行小样本比较。

DeepSeek 参考线回答：

- 平台是否能够用统一 API 同时承载自有模型和第三方模型；
- 两类供给在用户体验、回答质量和单次成本上的差异；
- 未来多 Provider、成本路由或质量路由是否值得继续实验。

DeepSeek 官方只运行并发 1 为主、并发 2 / 4 为辅的小样本，不探测其容量上限。官方模型与本地 Gemma 的 Tokenizer、模型规模和服务集群不同，因此 Token 数和吞吐不能直接当作硬件性能排名。

## 4. 测试负载

### 4.1 短问答

- 短输入、短输出；
- 主要观察 TTFT、端到端延迟与交互体验；
- 用于四条分层路径的基线比较。

### 4.2 内容生成

- 短输入、固定较长输出上限；
- 主要观察单请求 Output Tokens/s、系统 Aggregate Output Tokens/s、并发退化与 GPU 压力；
- 用于公网并发阶梯和稳定性测试。

### 4.3 长文本理解（时间允许时）

- 固定长输入、短输出；
- 主要观察 Prompt 处理、TTFT、上下文长度和显存变化；
- 不作为首轮必跑项。

### 4.4 质量参考集

使用 10～20 个固定问题，覆盖中文表达、指令遵循、事实核对、摘要、简单代码和推理。质量评价采用预先定义的 rubric；模型名称可在盲评表中隐藏，减少先入为主。

## 5. 执行顺序

### 阶段 0：安全与环境基线

1. 记录 Git release、域名、模型、LM Studio 版本、模型量化、上下文和采样配置。
2. 记录 Windows GPU、显存、驱动、CPU、内存和测试时模型占用。
3. 记录 ECS app / PostgreSQL / Redis、Tailscale、Runner 和公网健康状态。
4. 创建专用短期测试 Token；DeepSeek 使用独立 Key，由用户直接配置并自行保管。
5. 确认没有其他模型任务占用 LM Studio。

### 阶段 1：业务闭环验收

按照第 3.1 节逐项执行，保存脱敏截图、时间戳、请求 ID 和账务核对结果。先保证功能链闭环，再进入压力测试。

### 阶段 2：并发 1 分层基线

使用短问答分别运行 A、B、C、D 四条路径。每条路径先预热，再采集足够样本，用于定位固定开销和网络差异。

### 阶段 3：公网全链路并发阶梯

对本地 Gemma 的 D 路径依次运行并发 1、2、4、8、16；每档达到固定时长或固定完成请求数。若仍稳定，再由主测试负责人决定是否上探，不机械增加并发。

短问答和内容生成分别运行；关键拐点重复至少两轮。

### 阶段 4：瓶颈复核

在出现明显退化的并发档，回到 A / B / C 对照，并结合 GPU、显存、ECS CPU / 内存 / 网络、错误日志和数据库状态判断瓶颈。

### 阶段 5：稳定性测试

在准备对外声称的“已验证稳定并发”上运行约 30 分钟，确认错误率、延迟、资源占用和队列没有持续恶化，结束后服务可恢复到健康基线。完成验证后，再把已验证稳定并发的约 70%～80% 作为保守运行建议；两者必须分开报告。

### 阶段 6：DeepSeek 参考与质量对比

通过平台分别调用 Gemma 和 DeepSeek V4 Flash。性能参考使用相同 Prompt、输出上限和 non-thinking 模式；质量对比使用固定题集，并记录实际 Usage 和成本。

## 6. 指标与口径

### 6.1 请求指标

- 请求数、成功数、失败数、超时数；
- HTTP 状态与错误类型；
- TTFT P50 / P95；
- 端到端延迟 P50 / P95；
- 单请求 Output Tokens/s；
- Aggregate Output Tokens/s；
- 每分钟完成请求数；
- prompt、completion、reasoning 与 total tokens（Provider 可返回时）。

P95 至少需要 100 个有效样本才作为正式分位数，小于该样本量时只作为探索性结果；P99 仅在样本量足够时报告。Streaming 以收到第一个有效内容 Token 的时间计算 TTFT，不把 HTTP Header 到达时间误作首 Token。

### 6.2 资源指标

- GPU utilization、VRAM、温度、功耗（现场可获取时）；
- Windows CPU、内存；
- ECS CPU、内存、网络和容器健康；
- LM Studio 队列、错误或模型卸载信息；
- PostgreSQL / Redis 异常与应用错误日志。

### 6.3 稳定容量定义

“已验证稳定并发”必须同时满足：

- 若要表述“成功率不低于 99%”，关键档位至少完成约 300 个零失败样本；否则只能报告“本次观测为 N/N”，不得上升为 99% SLA；
- 无 OOM、服务崩溃或持续性健康异常；
- P95 TTFT 未发生不可控增长；
- 单用户生成速度仍处于可接受范围；
- 请求积压不持续增长；
- 停止加压后服务能够恢复到健康基线。

并发 1 基线完成后、进入高并发前，双方必须预先写下本次 Demo 的 TTFT、单用户生成速度和超时门槛及理由，避免看完结果再选择标准。最终报告同时给出相对退化曲线和面向用户的绝对体验，不只给一个并发数字；这些门槛属于本次 Demo 建议值，不是正式服务 SLA。

主容量测试使用 closed-loop 并发，表示持续在途请求数，不直接等于注册用户数或固定到达率。若时间允许，另做受硬性上限保护的短时 arrival-rate ramp，观察突发到达、排队与超时；若未执行，老板材料不得据 closed-loop 结果推导流量峰值承载能力。

## 7. 停止条件与故障处理

出现以下任一情况时停止继续加压：

- 连续请求失败或错误率明显超过目标；
- LM Studio OOM、崩溃、卸载模型或无法继续响应；
- GPU / CPU 温度或功耗达到用户确认的设备安全阈值；
- ECS app、PostgreSQL、Redis 或公网健康检查失败；
- P95 TTFT 或队列出现持续性、不可恢复的增长；
- 用户观察到 Windows 或 LM Studio 异常。

停止后保留现场，不立即修改模型、网络或平台配置。先记录错误、时间和资源状态，再决定恢复操作。任何故障注入都不属于主压力测试，必须另行确认。

## 8. 数据与 Secret 边界

- 所有测试 Token 和 Provider Key 只通过环境变量或用户后台配置读取；
- 测试配置强制限制最大并发、请求总数、运行总时长、单请求 `max_tokens`、上下文长度和 DeepSeek 预算，超限时工具拒绝启动；
- 使用专用测试用户、测试 Token、模型访问范围和可追踪但不含 Secret 的 run ID，避免与其他账务和日志混淆；
- Secret 不写入命令行参数、Git、CSV、JSON、日志、截图、报告或聊天；
- 原始结果记录模型、路径、时间、并发、Prompt profile、请求指标与脱敏错误类型；
- Prompt 与非敏感测试配置进入版本控制，原始测试结果是否提交需在采集后单独判断；
- DeepSeek 使用专用 Key、小额余额，并在测试后禁用或删除；
- 不读取或输出 ECS root-only Secret 文件内容。

## 9. 分工

### Codex 负责

- 设计和实现跨平台测试工具；
- 提供 macOS、Linux、Windows 的执行命令；
- 执行可自动化的公网 / ECS 测试；
- 解析 SSE、Usage、延迟与吞吐；
- 清洗和汇总脱敏数据；
- 绘制架构图、容量曲线和瓶颈证据图；
- 编写测试报告、老板汇报稿及 PPT / PDF / HTML；
- 在每个加压阶段检查停止条件和结果质量。

### 用户负责

- 在本地保管测试 Token 和 DeepSeek API Key，不回传 Key 值；
- 在平台后台配置 DeepSeek Channel 和模型价格；
- 确认 LM Studio 模型已加载且无其他任务；
- 提供非敏感的 GPU、显存、驱动和模型配置；
- 按步骤运行 Windows 侧测试工具和硬件监控；
- 观察 LM Studio 队列、错误、模型状态和设备安全状态；
- 完成必须通过浏览器进行的注册、登录、Token 和管理员日志验收。

### 共同检查点

1. 测试环境基线确认；
2. 业务闭环验收通过；
3. 并发 1 基线数据复核；
4. 每次上探并发前确认；
5. 稳定并发和瓶颈结论复核；
6. 对老板汇报中的事实、推断和未来规划分层确认。

## 11. 汇报叙事

老板版材料按以下顺序组织：

1. 为什么做：亚太 AI 推理服务与自有模型供给机会；
2. 已经做到：公网平台到 Singapore 模型的真实闭环；
3. 现场看到：登录、Playground、API Key、Streaming、Usage / Billing；
4. 数据说明：当前容量、用户体验和瓶颈；
5. 外部参照：DeepSeek 官方与本地 Gemma 的体验 / 成本 / 质量差异；
6. 商业含义：什么时候应该增加 GPU、优化 Serving、调整网络或引入多 Provider；
7. 下一步决策：Demo 后最值得投入的验证与产品工作。

所有汇报结论必须标注为“已验证事实”“本次测试推断”或“未来规划”，不把 Demo / PoC 表述为 Production 能力。
