# 网关容量测试设计

日期：2026-08-26
状态：已确认，待实施

## 1. 测试目标

本测试用于回答一个独立问题：在不受真实大模型推理速度影响时，当前公网服务链路能够稳定承载多少个同时进行的 API 请求。

测试覆盖：

- 公网 HTTPS 与 Cloudflare Tunnel；
- many-models 的 API Key 鉴权、模型路由、请求转发、用量记录与日志；
- 应用与 PostgreSQL、Redis 的协作；
- ECS 的 CPU、内存、网络、连接数、容器状态；
- 上游响应较慢时的连接保持、排队、超时和错误处理。

测试不覆盖：

- GPU、LM Studio 或真实模型的推理容量；
- 模型回答质量；
- Production SLA、高可用、跨可用区和故障恢复；
- “同时在线用户数”。用户行为频率不同，不能把并发请求数直接等同于用户数。

系统最终容量应理解为：`min(网关容量, 模型推理容量, 外部依赖容量)`。

## 2. 架构与请求路径

```text
MacBook（k6 压测发起端）
        │ 真实公网 HTTPS 请求
        ▼
Cloudflare Tunnel
        ▼
ECS many-models（鉴权 / 路由 / 计费 / 日志）
        │ Docker 内部网络
        ▼
Mock Provider（固定等待后返回 OpenAI-compatible 响应）
```

选择 MacBook 作为请求发起端，可以覆盖真实公网、DNS、TLS 与 Tunnel；Mock Provider 则放在 ECS 的应用内部网络中，避免把模拟模型自身的公网链路混入结果。

Mock Provider 使用临时独立容器：

- 不开放宿主机端口；
- 不修改生产 Compose 文件；
- 只加入 many-models 当前实际使用的 Docker 网络；
- 通过专用模型名与专用测试渠道隔离；
- 测试结束后可单独删除，不影响正式模型渠道。

## 3. 测试组件

### 3.1 Mock Provider

使用 Node.js 内置 HTTP 能力实现零业务依赖的异步服务，提供：

- `GET /health`：容器健康检查；
- `GET /v1/models`：返回专用模型 `mock-sleep-1s`；
- `POST /v1/chat/completions`：兼容 OpenAI Chat Completions；
- 非流式：默认异步等待 1 秒后返回固定 JSON；
- 流式：默认 100 ms 后返回首个 SSE chunk，再按配置间隔返回若干 chunk，以 `[DONE]` 结束；
- 只记录时间、请求 ID、模型、流式标记、模拟时长和状态，不记录 Prompt 或凭证。

等待必须使用异步 Timer，不能使用阻塞式 sleep，否则测到的是 Mock 自身线程阻塞能力。

### 3.2 负载发生器

使用 k6，通过官方 Docker 镜像在 MacBook 运行，不做全局安装。脚本从未跟踪的 `.env.local` 读取：

- `GATEWAY_CAPACITY_TARGET`：公开 API 地址；
- `GATEWAY_CAPACITY_MODEL`：专用模型名；
- `GATEWAY_CAPACITY_API_KEY`：普通用户生成的测试专用 API Key。

脚本和日志不得打印 API Key；结果写入已忽略的 `artifacts/benchmarks/gateway-capacity/<run-id>/`。

## 4. 工作负载与阶段

所有档位固定 Prompt、模型、输出规模、Mock 等待时间和超时，仅改变并发量。先做短测找拐点，再做稳定性验证。

### 阶段 0：Preflight

- 确认正式模型与页面当前可用；
- 确认 ECS CPU、内存、网络和容器监控可见；
- 只读确认应用容器、实际 Docker 网络及剩余资源；
- 部署临时 Mock，并从应用容器内验证可达；
- 创建只指向 Mock 的专用渠道与专用模型。

### 阶段 1：Smoke Test

- 非流式单请求；
- 流式单请求；
- many-models 日志出现专用模型和渠道；
- Mock 日志出现对应请求；
- LM Studio 与 DeepSeek 无新增调用，证明流量隔离成立。

### 阶段 2：非流式阶梯测试

- Mock 固定等待 1 秒；
- 初始并发档位：10、25、50、100、200、400；
- 每档约 2 分钟，档间短暂恢复；
- 根据错误率、延迟和资源水位提前停止，或在稳定时继续上探。

理论上，若额外开销很小，1 秒等待下并发数与 RPS 数值接近；实际差值可用于观察网关开销和排队。

### 阶段 3：流式连接测试

- 首包等待约 100 ms；
- 总连接保持约 3～5 秒；
- 从低于非流式拐点的档位开始；
- 重点观察长连接、首包延迟、连接中断与 ECS 网络/文件描述符。

### 阶段 4：稳定性测试

- 选择短测最大稳定容量的 70%～80%；
- 连续运行 30 分钟；
- 观察延迟漂移、内存增长、容器重启、连接堆积和数据库/Redis 异常。

## 5. 指标与停止线

核心指标：

- 并发请求数：同一时刻正在处理的请求数量；
- RPS：每秒完成的请求数；
- P50/P95/P99 端到端延迟；
- 额外网关延迟：端到端延迟减去 Mock 固定等待；
- 成功率、HTTP 状态码、超时率和连接中断率；
- ECS CPU、内存、网络吞吐、连接数；
- 应用、Mock、PostgreSQL、Redis 的 CPU、内存、NET I/O、重启与 OOM；
- 数据库连接池、Redis、日志和渠道状态中的异常。

任一条件满足即停止继续加压：

- 总错误率持续超过 1%；
- 429、502、503 或 504 持续出现；
- P95 额外网关延迟超过 1 秒并继续恶化；
- ECS CPU 持续 2 分钟超过 85%；
- 内存超过 80% 或呈持续增长；
- 出现连接池、文件描述符、端口或连接耗尽；
- 容器 OOM、重启、健康检查失败，或正式业务受到影响。

正式公网阶梯压测属于会影响线上资源的动作。只有在 Smoke Test、监控和停止手段均确认后，主 Agent 再向用户明确说明首个档位并取得开跑确认。

## 6. 证据与报告口径

每个档位保存：

- k6 原始摘要与结构化结果；
- 起止时间、配置、并发档位与模拟时长；
- ECS 和容器资源快照；
- many-models 与 Mock 的脱敏日志证据；
- 错误分类和停止原因。

最终报告给出：

- 最大短时无错误档位；
- 推荐稳定并发档位；
- 30 分钟稳定性结果；
- 非流式与流式差异；
- 首个瓶颈及其证据；
- 当前结果不能外推的边界。

短样本 P95/P99 只作探索，不表述为 SLA；Mock 测试结果只代表网关链路，不代表真实模型服务能力。

## 7. 分工

### 主 Agent

- 编写并验证 Mock、k6、监控和操作文档；
- 只读核对 ECS 运行态和 Docker 网络；
- 部署与清理临时 Mock 容器；
- 执行本地验证、Smoke Test 和经确认后的正式压测；
- 汇总证据并更新测试报告。

### 用户

- 在 BytePlus 控制台保持 ECS CPU、网络及可用的内存监控页面；
- 按主 Agent 给出的字段在 many-models 页面创建专用测试渠道；
- 凭证只保存在本地未跟踪环境文件，不回传具体值；
- 正式压测开始时确认线上业务无人使用并授权开跑；
- 必要时提供控制台监控截图和页面侧日志观察结果。

## 8. 清理与回滚

测试结束或触发停止线后：

1. 停止 k6；
2. 禁用或删除专用 Mock 渠道；
3. 停止并删除临时 Mock 容器；
4. 删除临时镜像或服务器临时文件；
5. 核验 `/api/status`、页面和正式模型单请求；
6. 确认应用、PostgreSQL、Redis 与 Tunnel 状态正常；
7. 保留脱敏测试证据，不保留凭证。

Mock 容器与专用渠道独立于正式应用发布，应用版本回滚不能替代上述清理步骤。
