# 网关容量测试报告

> 测试日期：2026-08-26
> 测试状态：已完成
> 测试工具：k6
> 测试范围：公网入口、Cloudflare、many-models、ECS 内部网络、数据库及 Mock Provider

## 1. 结论

这次测试把真实大模型替换成了固定延迟的 Mock 服务。这样可以暂时排除 GPU 和模型推理速度，只看公网入口、many-models 和 ECS 服务本身能承受多大的请求压力。

短时测试得到的结果是：

- 非流式请求在 100 VU 下通过，提升到 200 VU 后触发延迟停止线。
- Streaming 请求在 25 VU 下通过，提升到 50 VU 后触发延迟停止线。
- Streaming 20 VU 连续运行 30 分钟，共完成 42,779 个请求。其中 42,773 个返回 2xx，6 个返回 HTTP 503，错误率为 0.014%。
- 30 分钟内，核心容器一直处于 healthy 状态，没有重启，也没有发生 OOM。many-models 的内存没有持续增长。

服务器 CPU 和内存没有先到极限。压力继续增加时，最先变差的是请求的长尾延迟，同时出现了少量 5xx。因此，当前需要先查清高压力下的链路等待和 6 次 HTTP 503，再讨论继续扩容。

这里的 VU 是压测程序中的虚拟执行者，不是实际用户数。100 VU 通过不能写成"系统支持 100 个用户"。真实业务容量还要同时考虑模型推理能力，最终取网关容量和模型容量中较小的一个。

## 2. 为什么要做这项测试

此前的测试已经测出了 Gemma 4 31B 在 RTX 4090 和 LM Studio 上的推理表现，但那组结果混合了模型计算、GPU、网络和网关开销。只看那组数据，很难判断请求变慢究竟卡在哪里。

本轮把模型替换成固定延迟 Mock，主要回答两个问题：

1. 不考虑模型推理时，公网和 ECS 上的 many-models 能处理多大的请求压力。
2. 压力升高后，系统先出现延迟、错误，还是 CPU、内存和容器异常。

这项测试不评价模型质量，也不测试 GPU 算力、真实模型 TTFT、ITL 或生产 SLA。

## 3. 测试链路

压测请求从 MacBook 发出，走的仍然是用户实际访问时使用的公网链路。Mock 放在 ECS 内部，与 many-models 使用同一个内部网络，而且没有开放宿主机端口。

```text
MacBook / k6
    ↓ HTTPS 公网请求
Cloudflare
    ↓
many-models / ECS
    ↓ ECS 内部网络
Mock Provider
    ↓
固定延迟的 JSON 或 SSE 响应
```

把发压端放在 MacBook 上，可以保留公网和 Cloudflare 的实际影响。把 Mock 放在 ECS 内部，则可以保留 many-models 到上游服务的真实调用方式。如果把 Mock 和 k6 都放在本机，测到的就主要是本机性能，不能代表当前部署链路。

## 4. Mock 如何模拟模型响应

Mock 提供非流式和 Streaming 两种响应：

| 模式 | 模拟方式 |
|---|---|
| 非流式 | 收到请求后固定等待 1000ms，再返回 OpenAI-compatible JSON |
| Streaming | 约 100ms 后返回第一个 SSE 数据块，共返回 4 块，块间隔约 100ms |

Mock 返回固定模型名和固定内容。k6 会检查 HTTP 状态、Content-Type、返回模型名和流式结束标记，防止请求误入 Gemma、DeepSeek 或其他正式渠道。

正式压测期间关闭 Mock 的逐请求日志，避免日志写入本身成为新的性能瓶颈。Mock 容器限制为 1 个 CPU、512 MiB 内存、只读文件系统和非 root 用户，并且不向公网发布端口。

## 5. 测试方法

### 5.1 Smoke 检查

先用 1 个 VU 顺序发送一条非流式请求和一条 Streaming 请求。只有下面几项都正常，才继续加压：

- 两条请求均返回 HTTP 200。
- JSON 和 SSE 格式正确。
- 返回模型名是 `mock-sleep-1s`。
- many-models 日志显示请求进入临时 Mock 渠道。
- 正式 Gemma 和 DeepSeek 渠道没有收到这批请求。

### 5.2 短时阶梯

每个正式档位运行约 2 分钟。非流式依次测试 5、10、25、50、100 和 200 VU；Streaming 依次测试 5、10、25 和 50 VU。达到停止线后不再继续提高档位。

本轮使用固定 VU 闭环模型。每个 VU 发出请求后，会等这次请求结束再发下一次。因此，它测的是固定并行执行者下的持续处理能力，不是用户在某个时刻突然同时到达的开放流量。

### 5.3 30 分钟稳定性

Streaming 短时通过档位为 25 VU。稳定性测试取其 80%，即 20 VU，连续运行 1800 秒。测试期间每分钟检查 many-models、PostgreSQL、Redis 和 Mock 容器的 CPU、内存、健康状态、重启次数和 OOM 状态。

## 6. 主要指标

| 指标 | 怎么理解 |
|---|---|
| VU | k6 中同时运行的虚拟执行者，不等于注册用户或在线用户 |
| RPS | 整条公网链路每秒完成的请求数 |
| 端到端延迟 | 从发出请求到完整响应结束所用的时间 |
| P50 | 一半请求不超过这个时间，可理解为多数请求的常见表现 |
| P95 | 95% 的请求不超过这个时间，用来观察慢请求和长尾 |
| HTTP TTFB | 从发出请求到收到 HTTP 首字节的时间。本轮用它观察 Streaming 首包，不等于真实模型 TTFT |
| 非流式额外开销 | 端到端延迟减去 Mock 固定的 1000ms sleep |
| 错误率 | HTTP 状态或响应协议不符合预期的请求占比 |
| 协议有效率 | JSON 或 SSE 响应格式、模型名和结束标记均符合预期的比例 |

停止线设置如下：

- HTTP 错误率必须低于 1%。
- 协议有效率必须高于 99%。
- 非流式额外开销 P95 必须低于 1000ms。
- Streaming HTTP TTFB P95 必须低于 1000ms。
- ECS CPU 持续两分钟超过 85%、内存超过 80%、容器重启、OOM 或健康检查失败时，人工停止测试。

错误率和协议停止线在 10 秒后开始判断。延迟停止线至少收集 30 秒样本，避免少量公网冷连接在低档位造成误判。

## 7. 短时测试结果

### 7.1 非流式

| VU | 完成请求 | RPS | 错误率 | 端到端 P50 | 端到端 P95 | 额外开销 P95 | 结果 |
|---:|---:|---:|---:|---:|---:|---:|---|
| 5 | 416 | 3.43 | 0 | 1.432s | 1.536s | 536ms | 通过 |
| 10 | 830 | 6.84 | 0 | 1.434s | 1.578s | 578ms | 通过 |
| 25 | 1,988 | 16.40 | 0 | 1.438s | 1.948s | 948ms | 通过 |
| 50 | 3,978 | 32.66 | 0 | 1.439s | 1.928s | 928ms | 通过 |
| 100 | 8,248 | 67.92 | 0 | 1.433s | 1.527s | 527ms | 通过 |
| 200 | 2,412 | 109.64 | 0.041% | 1.647s | 2.120s | 1120ms | 停止 |

200 VU 运行约 22 秒后自动停止。该档出现 1 次其他 5xx，额外开销 P95 达到 1120ms，超过 1000ms 停止线。停止时还有 200 个在途请求被 k6 中断。由于延迟边界已经出现，本轮没有继续测试 400 VU。

### 7.2 Streaming

| VU | 完成请求 | RPS | 错误率 | 端到端 P50 | 端到端 P95 | HTTP TTFB P95 | 结果 |
|---:|---:|---:|---:|---:|---:|---:|---|
| 5，首轮 | 48 | 4.72 | 0 | 未采集 | 1.537s | 1491ms | 小样本误触发 |
| 5，同条件复测 | 701 | 5.81 | 0 | 0.833s | 0.906s | 690ms | 通过 |
| 10 | 1,417 | 11.75 | 0 | 0.833s | 0.881s | 635ms | 通过 |
| 25 | 3,585 | 29.68 | 0 | 0.832s | 0.848s | 635ms | 通过 |
| 50 | 1,674 | 52.31 | 0 | 0.850s | 1.382s | 1171ms | 停止 |

第一次 5 VU 测试只运行了约 10 秒，完成 48 个请求。少量公网冷连接长尾把 TTFB P95 推到 1491ms，触发了原来的 10 秒延迟停止线。同条件复测完成 701 个请求，全部成功，TTFB P95 为 690ms。因此，第一次结果不作为容量不足证据，延迟停止线的观察窗口随后调整为 30 秒。

50 VU 运行约 32 秒后，TTFB P95 达到 1171ms 并触发停止。该档已完成的 1,674 个请求在 HTTP 状态和响应协议上均有效，停止原因是首包长尾超过预设边界。本轮没有继续测试 Streaming 100 VU。

| HTTP 2xx | 42,773 |
| HTTP 503 | 6 |
| 错误率 | 0.0140% |
| 协议有效率 | 99.9860% |
| RPS | 23.76 |
| 端到端 P50 | 0.834s |

这轮测试通过了预设阈值，但不能写成零错误。6 个请求返回 HTTP 503，占全部请求的 0.014%。当前聚合结果无法确认这些 503 来自 Cloudflare、many-models、数据库连接还是 Mock 上游，需要再对照各段日志。

## 9. 服务器资源表现

30 分钟内，many-models、PostgreSQL、Redis 和 Mock 容器始终为 healthy，重启次数为 0，也没有发生 OOM。

| 组件 | 观察结果 |
|---|---|
| many-models | CPU 多数时间约 5.28% 到 10.48%；内存约 73 MiB 到 85 MiB，没有持续增长 |
| PostgreSQL | CPU 通常约 3.60% 到 6.91%，出现过一次约 28.69% 的采样峰值；内存约 64 MiB 到 119 MiB，测试后连接数恢复 |
| Redis | 资源占用较低，最终约 10.84 MiB 内存 |
| Mock Provider | CPU 通常约 1%，偶有约 9% 的采样；内存从约 37.3 MiB 波动到 40.5 MiB，低于 512 MiB 限制 |

测试结束后的空闲快照显示，many-models 内存约 83.97 MiB，PostgreSQL 内存约 96.15 MiB，PostgreSQL 进程数恢复到 9。ECS 当时共有 15,737 MiB 内存，可用约 12,539 MiB。

这些数据说明本轮停止边界不是由 CPU、内存或容器崩溃直接造成的。高档位先出现的是 P95 延迟上升和少量 5xx。

## 10. 测试过程中的两项校正

一轮非流式测试在本机 Docker 启动阶段遇到 socket 问题，没有请求发到服务器。这是测试工具启动失败，不计入服务器结果。

Streaming 5 VU 首轮暴露了另一个问题。10 秒窗口内样本太少，个别公网冷连接足以推高 P95。复测确认服务本身正常后，延迟停止线改为等待 30 秒再判断。错误率和协议有效率仍保持 10 秒快速判断，以便服务真正报错时及时停止。

本次 k6 汇总配置没有保存 P99，历史数据无法事后补算。报告保留 P50、P95 和 Max，但 Max 不等于 P99。测试脚本已经加入 P99，后续运行会直接保存该指标。

## 11. 这次测试告诉了我们什么

排除模型推理后，非流式 100 VU 和 Streaming 25 VU 是本轮短时测试最后通过的档位。这两个数字与真实模型并发采用不同口径，不做直接换算。

继续提高压力时，延迟比 CPU 和内存更早越过边界。只看服务器平均 CPU 使用率，会高估系统还能承受的压力。

Streaming 比非流式更早遇到边界。Streaming 连接需要驻留一段时间，也更容易受到首包等待和连接管理的影响。

30 分钟运行说明系统在 20 VU Streaming 下总体稳定，但仍出现 6 次 HTTP 503。错误率很低，却不能忽略。商业化前需要知道这些错误从哪里产生，以及是否会集中影响同一批用户。

## 12. 不能从这次测试推出什么

- 不能把 100 VU 解释成 100 个用户。
- 不能把本轮结果当成 Production SLA。
- 不能据此判断 Gemma、DeepSeek 或 GPU 的真实容量。
- 不能由聚合数据判断 6 次 HTTP 503 的具体来源。
- 不能精确拆分 Cloudflare、many-models、PostgreSQL 和 Mock 各自占用了多少延迟。
- 不能说明突发流量下系统仍会得到相同结果，因为本轮使用的是固定 VU 闭环模型。

## 13. 后续工作

下一轮应先查询 many-models、Cloudflare 和 Mock 的对应时间窗日志，定位 6 次 HTTP 503。随后使用开放到达率模型，按固定 RPS 发起请求，观察突发和持续流量下的排队、拒绝和恢复情况。

如果这套系统准备进入商业试用，还需要在计划使用的真实服务器上重复多轮测试，并把网关测试与真实模型测试组合起来。对外可用容量应以两者中较小的结果为准。
