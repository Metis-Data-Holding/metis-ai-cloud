> 测试日期：2026-08-24（模型）、2026-08-26（网关 Mock）
>
> 状态：模型容量、稳定性、DeepSeek 参考、加权路由与固定延迟 Mock 网关容量测试均已完成

## 1. 结论摘要

- 公网完整链路在并发 4 下完成 30 分钟稳定性验证：1308 个请求成功、0 个请求错误。
- 原始 4 槽位短时阶梯中，并发 6 开始排队退化；并发 8 的 TTFT 中位数达到 6.80 秒，越过 5 秒停止线。
- 当前建议老板现场 Demo 使用并发 1～2；本次环境下验证过的稳定并发为 4。
- 将 LM Studio 并行预测槽位从 4 放宽到 6 后，总吞吐仅提高约 9.9%，但 TTFT P50 增加约 72.9%、ITL P50 增加约 29.5%；4 槽位确实限制了部分吞吐，但底层推理竞争和调度成本才是继续扩容的主要约束。
- 新参数实验期间 GPU 没有过热、显存增长或 OOM；显存始终约 23.9 GB，说明高空闲显存主要来自模型权重、KV Cache 和运行时缓冲区常驻，而不是持续计算负载。
- DeepSeek V4 Flash 的后续 Token 输出明显更快，但默认 thinking 造成了数量级的成本放大；生产接入必须强制限制 thinking、输出 Token 和用户额度。
- 排除真实模型推理后，网关公网链路的短时固定 VU 闭环档位为：非流式 100 VU 通过、200 VU 触发停止线；流式 25 VU 通过、50 VU 触发停止线。流式 20 VU 连续 30 分钟完成 42779 请求，其中 6 次 HTTP 503，错误率 0.014%。

## 3. 方法与证据口径

- 使用 OpenAI-compatible `/v1/chat/completions` 和 Streaming。
- 固定模型、Prompt 规模、Temperature 和输出上限；阶梯间不修改 LM Studio 参数。
- 短时阶梯为并发 4、6、8；每档设置零容忍错误停止条件。
- 候选并发 4 运行 1800 秒稳定性测试。
- 将 `Max Concurrent Predictions` 调整为 6 后，保持其余条件不变，分别以并发 4、5、6 运行 24 请求短时参数实验。
- Windows 使用 `nvidia-smi` 每秒记录 GPU 利用率、显存、温度和功耗；同步观察 LM Studio 服务日志。
- 原始 GuideLLM 结果和 GPU CSV 保留在未跟踪本地目录；报告仅使用脱敏聚合值。
- 短时档位样本不足 100，其 P95 仅为探索性；30 分钟测试的 1308 个成功样本可用于本次环境的稳定性判断，但不等于 Production SLA 或 HA 验证。

### 指标怎么读

| 指标 | 通俗解释 | 读数方向 |
|---|---|---|
| 并发 | 同一时刻正在处理的请求数，不等于注册用户数或在线用户数 | 在体验可接受前提下，越高越好 |
| TTFT | Time To First Token：用户发出请求后，等到第一个字出现的时间；会受到排队、网络和模型预处理影响 | 越低越好 |
| ITL | Inter-Token Latency：第一个字出现后，后续字词之间的平均间隔；可理解为模型“说话是否流畅” | 越低越好 |
| 端到端延迟 | 从请求发出到最后一个 Token 完成的总时间；输出越长，通常越久 | 固定输出长度后，越低越好 |
| 聚合输出吞吐 | 整套服务每秒输出的 Token 总量，不是单个用户的说话速度 | 在稳定且体验可接受时，越高越好 |
| P50 / P95 / P99 | 分别代表 50%、95%、99% 请求不会超过该数值；P95/P99 用来观察少数用户的“长尾等待” | 越低、越稳定越好 |
| 成功 / 错误 / incomplete | 成功是完整响应；错误是服务失败；incomplete 是测试硬停止时仍在途的请求，不能自动等同于服务故障 | 必须分开统计 |

一句话记忆：**TTFT 看“多久开口”，ITL 看“开口后说得顺不顺”，端到端延迟看“多久说完”，聚合吞吐看“整套系统一秒能说多少”。**

## 9. 加权路由功能测试

目标是让客户端始终请求公开模型 `google/gemma-4-31b`，由 New API 在同组、同优先级的
本地 Gemma 与 DeepSeek 渠道间按权重随机选择；DeepSeek 渠道再通过 Model Mapping 将
上游模型改写为 `deepseek-v4-flash`。该能力不需要修改源码，配置与风险研究见
[New API 加权路由研究](./new-api-routing-research.md)。

本轮计划采用 Gemma / DeepSeek 权重 70 / 30，以 New API 日志中的渠道字段为主，并与
DeepSeek 官方后台和 LM Studio 日志交叉核对。

首次配置时 DeepSeek 为 `Priority=10`、Gemma 仍在较低优先级，导致流量全部进入
DeepSeek。将 Gemma 校正为 `Priority=10, Weight=70` 后，两条渠道进入同一候选层。

校正后的执行结果如下：

| 项目 | 结果 |
|---|---:|
| 20 个非流式短请求 | 20 / 20 成功，0 错误 |
| 可观察响应模型分布 | Gemma 13、DeepSeek 7，即 65% / 35% |
| 目标权重 | Gemma 70、DeepSeek 30 |
| 30 请求 Streaming 批次 | 30 / 30 成功，0 错误 |
| Streaming 时间窗 | 15:02:43～15:03:57 |
| TTFT P50 / P95 | 0.943s / 1.335s |
| 延迟 P50 / P95 | 2.30s / 3.10s |
| ITL P50 / P95 | 41.3ms / 46.0ms |

20 个非流式样本中实际分布为 65/35，与 70/30 的随机分流目标接近，证明同一公开 Gemma
模型名可以在后台选择本地 Gemma 或映射到 DeepSeek。30 个 Streaming 请求全部完整成功，
证明两条渠道在同一公开接口下具备基本协议兼容性。本项核心功能判定为通过；Streaming
批次的逐渠道精确命中数仍需用 New API 后台 `Channel` 字段交叉确认，不能由聚合性能指标
反推。

GuideLLM 在混合 Streaming 批次记录的输出 Token P95 高于配置的 32 Token 上限，当前不将
其作为可靠计费口径；后续需结合 New API 逐笔 Usage 判断是流式指标解析、参数上限未穿透，
还是上游响应差异。

## 10. 网关容量与固定延迟 Mock 测试

### 目标与边界

这是一项网关容量测试（Gateway Capacity Test）：macOS 上的 k6 经真实公网、Cloudflare 和 many-models 访问 ECS 内网 Mock Provider。Mock 用固定延迟模拟上游处理，不调用 LM Studio、DeepSeek 或 GPU，用于隔离观察网关、数据库、容器、连接和公网链路的承载能力。

- 非流式 Mock：固定等待 1000ms 后返回 JSON。
- Streaming Mock：约 100ms 后返回首个数据块，共 4 块，块间隔约 100ms。
- 负载模型：固定 VU 闭环；每个 VU 等待上一个请求完成后再发下一个。
- 停止线：HTTP 错误率 <1%、协议有效率 >99%；非流式额外开销 P95 <1000ms，Streaming HTTP TTFB P95 <1000ms。

VU 是“虚拟执行者”，不是注册用户数或同时在线用户数。RPS 是公网完整链路每秒完成的请求数；TTFB 是收到 HTTP 首字节的时间，在本次 Mock 测试中作为 Streaming 首包体验的近似指标，不等同于真实模型 TTFT。

## 11. 瓶颈判断

### 高概率结论

- 4 槽位基线下，超过并发 4 后 TTFT 显著增加，证明预测槽位会形成请求排队门槛。
- 放宽到 6 槽位后吞吐从 49.1 墧至 54.0 tok/s，但 TTFT、ITL 和端到端延迟的增幅远高于吞吐增幅。
- 并发 5/6 的平均 GPU 利用率没有高于并发 4；显存、温度和功耗稳定，无 OOM 或资源增长。
- 既有 30 分钟稳定性测试无 OOM、显存增长、过热、模型卸载、请求错误或 LM Studio 日志异常；本轮参数实验 API 零错误，但 LM Studio 后台日志尚待人工确认。

因此，4 个预测槽位是可见的第一道并发门槛，但不是唯一瓶颈；放宽门槛后，LM Studio / 推理引擎的调度、共享资源竞争以及单卡推理效率成为主要约束。当前证据不支持“GPU 还有大量空闲算力，所以并发可以继续线性提高”。

### 尚不能声称

- 不能把并发 4 等同于可注册用户数、在线用户数或 Production SLA。
- 没有验证 HA、故障转移、长上下文、多轮会话、复杂 Prompt 或多模型同时加载。
- 测试端到 Singapore LM Studio 的直连路径受当前 Tailnet ACL、Windows 防火墙或入站策略限制而不可达；为避免降低安全策略，本次没有做直连 A 路径差分。
- 因缺少安全可比的分段路径测试，不能把公网链路每一段的耗时精确拆开。
- Mock 测试不包含真实模型推理；最终用户容量仍取决于“网关容量”与“模型容量”中更小的一个。

## 12. 建议

1. 老板现场 Demo 控制在并发 1～2，并预热模型。
2. 当前环境仍以并发 4 作为已验证稳定并发；`Max Concurrent Predictions = 6` 只通过短时测试，不替代并发 4 的 30 分钟稳定性证据。
3. Demo 和交互业务建议恢复或限制为 4 个实际并行请求；若批处理业务愿意接受更慢的单请求体验，可再对 6 槽位执行 30 分钟稳定性测试。
4. 当前显存只剩约 660 MiB，不继续提高预测槽位；后续扩容优先测试更低 Context、更小量化/模型、其他推理引擎或新增 GPU。
5. DeepSeek 请求由平台强制设置 thinking 策略、输出上限、单 Token 额度和预算告警。
6. 商业化前补充不同 Prompt / 输出长度、长上下文、多轮对话、质量评估、成本模型和故障恢复测试。
7. 网关商业化补测采用开放到达率模型，对 6 次 HTTP 503 做日志级归因，并在真实服务器上重复多轮以形成更可靠的容量区间。
